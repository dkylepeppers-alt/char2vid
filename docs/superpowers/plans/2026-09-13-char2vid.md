# char2vid Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The linked subsystem plans provide the executable task breakdown.

**Goal:** Deliver the complete Android-first image → character → video studio with a durable local gallery, dynamic Nano-GPT integration, sound, and finished-video export.

**Architecture:** One web UI and domain model use native or browser storage adapters. A small self-hosted service owns provider credentials, queued jobs, and temporary media staging. Character, shot, graph, and edit revisions preserve continuity and provenance across the workflow.

**Tech Stack:** React, TypeScript, Vite, Zod, Capacitor 8, Kotlin/Room/Media3, Dexie/OPFS, Node 22+, Fastify/SQLite, FFmpeg, Vitest, Playwright, GitHub Actions.

**Spec:** [Product and architecture design](../specs/2026-09-13-char2vid-design.md).

## Global Constraints

- Android API 26 is the product support floor.
- Node 22+ and Capacitor 8 are the initial platform baseline.
- Nano-GPT is the sole AI provider.
- Originals and approved outputs are never cache.
- All available model records must remain discoverable by exact ID.
- Potentially accepted media submissions are never retried automatically.
- Credentials and temporary signed URLs are excluded from portable exports and logs.
- Automated fixture tests must not spend provider credits.

## Planning status

Research/design/plan files are the deliverable of this planning pass. No application code, running service, or APK exists yet. Implementation checkboxes begin unchecked. Dependency versions and generation contracts must be validated during the relevant tasks; the research snapshot is dated evidence, not a frozen model registry.

## Evidence-first implementation rules

1. Read the spec and relevant research before each subsystem. Resolve a contract conflict through a captured response or a documented restricted behavior; do not invent fields.
2. For risky behavior, write the specified failing behavioral test, observe failure for the intended reason, implement the smallest coherent unit, then rerun the focused check.
3. For layout/documentation-only work, inspect/render the result; do not create tests that merely assert the implementation's own text.
4. Commit each independently usable task. Commit source and generated Android project configuration together when required to reproduce builds.
5. Never make a paid call in automated CI. Manual provider checks use a configured key and an explicit small spending budget at execution time.
6. Mark a checklist complete only with its stated evidence. A mocked test is not native-device or real-provider proof.
7. Keep active drafts and original assets intact during migrations and repairs. Use a task branch/worktree once the repository has implementation history.

## Contract verification gate before paid media integration

P1 produces `docs/validation/provider-contracts.md` with one row per route family. It records:

- Exact base URL, method/path, auth header, request fields, response variants, date, and sources.
- Accepted input roles, maximum items, formats, pixel/byte/duration limits, and treatment of encoded size.
- Any differences between advertised controls and accepted request values.
- Whether results are inline bytes/base64/URLs or jobs; polling method/body; recoverability and expiry.
- Whether capability evidence is only metadata, an authored fixture, or an actual budgeted generation.

Priority families are normalized image generation, image edits/masks, common image/video reference routes, Seedream/Seedance records actually present at that time, async image special cases, TTS/music, timestamped STT, and media utilities. This priority controls validation order, never visibility of the remaining models.
